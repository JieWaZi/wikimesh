# Repository Guidelines

## Project Structure & Module Organization

Wikimesh is a Go CLI and SDK project. The CLI entrypoint is `cmd/wikimesh`, and command construction lives under `internal/cli`.

Current package layout:

- `cmd/wikimesh`: process entrypoint only; keep startup glue here.
- `internal/cli`: root command assembly and top-level command wiring.
- `internal/cli/wiki`: Wiki command family: `init`, `read`, `search`, `glossary`, `repo`, and `check`.
- `internal/cli/qmd`: qmd command family: collection, update, search, query, embed, and model commands.
- `internal/cli/skill`: runtime skill command wiring.
- `internal/app/qmdapp`: application helpers that let CLI code use `pkg/qmd`.
- `internal/app/wikiapp`: Wiki repo config, page parsing, Markdown table helpers, and qmd-backed Wiki search adaptation.
- `internal/app/wikiinit`: `wikimesh init` business logic: workspace creation, repo config registration, templates, gitignore, and skill installation orchestration.
- `internal/app/skillapp`: runtime skill source resolution, discovery, installation, and reference-group sync.
- `internal/app/updateapp`: self-update service.
- `internal/ui`: CLI logo, Chinese help text, interactive controls, and user-facing messages.
- `pkg/qmd`: public qmd SDK facade.
- `pkg/qmd/embed`, `pkg/qmd/extract`, `pkg/qmd/index`, `pkg/qmd/llamaruntime`: lower-level qmd implementation packages.
- `skills/devwiki`: built-in DevWiki runtime skills.

Tests sit beside implementation files as `*_test.go`.

## Code Boundaries

Keep these boundaries explicit:

- `cmd/wikimesh` must not contain command behavior. It should delegate into `internal/cli`.
- `internal/cli` owns Cobra commands, flags, arguments, terminal IO, JSON/Markdown output shape, and interactive prompting. It should not own durable business rules or storage behavior.
- Wiki commands must live under `internal/cli/wiki/<command>` unless a command is truly not part of the Wiki family.
- `internal/cli/wiki/init` should stay as command orchestration, option normalization, and prompt/skill selection. Workspace creation and config writes belong in `internal/app/wikiinit`.
- `internal/cli/wiki/repo` is small enough to keep its add/info/link/use handlers in `command.go`; do not split one tiny subcommand per file.
- `internal/app` packages should be UI-free and Cobra-free. They may return errors, but user-facing phrasing and help text belong in `internal/ui`.
- `internal/app/qmdapp` is the CLI-to-`pkg/qmd` adapter. CLI code should not directly reach into qmd SQLite, FTS, chunk, vector, or llama runtime internals.
- `pkg/qmd` is the public SDK boundary. Do not expose SQLite, FTS, chunk, vector table, or llama runtime implementation details through this API.
- qmd lower-level packages must not import `internal/cli` or depend on CLI concepts.
- Runtime workspace templates generated by `wikimesh init` live under `internal/app/wikiinit/template/docs`; runtime skill assets live under `skills/devwiki`.

## File Organization

Prefer files grouped by responsibility, not by individual helper function.

- Do not create `types.go`, `helpers.go`, or one-function files unless the package is already large enough that the split improves navigation.
- Keep compact command families together when their handlers are short and share the same config surface.
- Split files when there is a clear durable boundary such as `config`, `page`, `search`, `service`, `workspace`, or `repo`.
- Avoid moving code only to make a package look flatter; move code when it clarifies ownership or removes a dependency leak.
- If structural boundaries matter, add or update focused structure tests like `internal/cli/structure_test.go`.

## Build, Test, and Development Commands

- `make build`: build the default binary at `.wikimesh/bin/wikimesh`.
- `make test`: run `go test ./...` with the repository-local Go cache.
- `make package`: package the binary and optional llama.cpp runtime files.
- `go run ./cmd/wikimesh --help`: run the CLI locally without installing it.
- `env -u GOROOT GOCACHE=$(pwd)/.cache/go-build go test ./...`: use this when local Go toolchain caches report version mismatches.
- `git diff --check`: verify whitespace and patch formatting before handoff.

## Coding Style & Naming Conventions

Run `gofmt` on changed Go files. Keep package names short and lowercase.

Comments and naming:

- New or updated Go comments should use Chinese unless an external API, protocol, or specification requires English.
- Struct fields must have Chinese comments when the struct is exported or important to package behavior.
- Key functions and non-obvious internal steps should have Chinese comments explaining intent, not line-by-line narration.
- Keep user-facing CLI text in `internal/ui`; do not scatter display strings through command implementations.

Implementation style:

- Prefer existing local helpers and package patterns over introducing new abstractions.
- Preserve existing CLI behavior, config formats, command names, flags, and public `pkg/qmd` APIs unless the task explicitly asks for a behavior change.
- Use structured parsers/APIs when available; avoid ad hoc string manipulation for config and structured documents.
- Keep changes scoped to the requested module and boundary. Do not mix unrelated cleanups into feature or refactor patches.

## Testing Guidelines

Use Go's standard `testing` package. Name tests `Test...` and keep them near the code they validate.

Add focused tests for:

- CLI command behavior, help/output contracts, and option normalization.
- Wiki repo config read/write behavior.
- qmd search/query semantics and public API changes.
- Package-boundary or file-layout rules when refactoring structure.

Before handing off code changes, run `make test` or:

```sh
env -u GOROOT GOCACHE=$(pwd)/.cache/go-build go test ./...
```

For CLI or architecture refactors, also run the relevant focused package tests and `git diff --check`.

## Documentation Guidelines

Keep documentation examples aligned with actual `wikimesh --help` output and current Go code. When command structure, config layout, or init workspace output changes, update `README.md` and any affected runtime templates.

Do not describe old paths such as `internal/cli/common`, old flat Wiki command packages, or generated `config/project.yaml` unless documenting migration history.

## Commit & Pull Request Guidelines

The current history is short and mixed (`init`, `finit`, `fix: action编译失败`). Prefer concise, imperative commit messages; use a Conventional Commit prefix such as `fix:` or `feat:` when it clarifies scope. Pull requests should describe the problem, summarize the change, list verification commands, and note any CLI behavior, config, or documentation impact. Include screenshots only for UI-facing changes.

## Agent-Specific Instructions

Check for deeper `AGENTS.md` files before editing subdirectories. Do not overwrite user changes in a dirty worktree. If unrelated files are already modified or untracked, leave them alone unless the current task requires touching them.

For behavior-preserving refactors, treat behavior as frozen: move and regroup code, but do not change command names, flags, output contracts, config formats, or public SDK APIs. Verify with tests before claiming the work is complete.
